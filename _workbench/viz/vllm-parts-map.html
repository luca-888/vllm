CPU 准备和 GPU 循环分进程

第 4 站是边界

问题
分词、解码、图像预处理都是 Python 里的 CPU 活。和 GPU 循环放在一个进程，谁忙谁就卡住对方。
做法
前端进程做完所有准备，只把 token 和张量交给引擎核心。引擎核心是一个不被打断的忙循环。
代价
每个请求多一次序列化。视频的 pixel_values 很大，所以大张量另走共享内存。

每一步重新组 batch

第 5 站

问题
请求长短不一、随时到达。等凑齐一批再跑，短请求会被长请求拖住。
做法
调度器每步按一个 token 预算挑请求：在跑的各给一个 decode token，剩下的预算分给新请求的 prefill，长 prompt 可以分几步吃完。
代价
batch 形状每步都变，这直接逼出了下面第四个决定。

KV cache 分页，按内容哈希复用

第 5 站分配，第 7 站读写

问题
每个请求的上下文长度事先不知道，连续分配会留下大量碎片。
做法
显存切成定长 block，请求按需领取，用一张 block table 记录映射。block 按 token 内容的哈希登记，相同前缀的新请求直接复用。
代价
注意力 kernel 要经 block table 间接寻址。前缀必须逐 block 完全一致才命中。

GPU 上只跑固定形状

第 7 站

问题
逐个算子从 Python 下发，每步的启动开销在小 batch 的 decode 上占比很高。
做法
输入写进常驻 buffer，batch 补齐到预先录好的几种大小，再回放录制好的 CUDA graph。纯 decode 的 batch 用整图，混有 prefill 的用分段图。
代价
录制时没进图的输入，回放时就改不了。#43776 就是这一类问题：多模态 embedding 没进整图。

多模态等于占位 token 加后填 embedding

第 3 站占位，第 6 站算，第 7 站填

问题
调度器和 KV cache 只认 token 数，但图像和视频不是 token。
做法
前端先算出这段视频会占多少个位置，在 prompt 里放等量的占位 token。到 worker 里 encoder 才算出真正的 embedding，覆盖到这些位置上。
代价
前端算的占位数必须和 encoder 实际输出的个数完全相等，也必须和 HF processor 的算法一致。视频方向的大多数 bug 出在这里。

vllm bench 怎么选

你想知道用哪个注意
serve线上用户感受到的延迟和吞吐要先 vllm serve。TTFT 把第 1 到 7 站全算进去，定位不了是哪一站。
throughput不考虑到达节奏时，引擎最多能跑多快所有 prompt 一次性提交，没有排队效应，数字比线上乐观。
latency某个固定 batch 形状下，模型前向本身多快输入是合成 token，前端几乎不参与。比较 kernel 或编译改动用它。
mm-processor多模态预处理和 encoder 各花多久从 processor 开始计时，解码不在内。自带的 random-mm 视频每帧是随机像素。
startup冷启动和热启动要多久与单个请求无关。
sweep一组参数里哪个配置最好自己起停服务并反复跑 serve，结果可画成曲线或帕累托前沿。

serve 的四个时间：TTFT 是首 token 时间，TPOT 是之后每个 token 的平均时间，ITL 是相邻 token 的间隔，E2EL 是整个请求的时间。goodput 是满足你设定的延迟上限的请求每秒完成数。
